# 4v4 doubles with switching

## What a player can do

Keep the existing endgame editor and add optional reserves to each side. The first release lets a player bring up to four Pokémon, choose the two starting leads, and leave reserve slots empty for smaller positions. A six-Pokémon import lets the player mark four to bring and two to lead. Automatic bring-four and lead selection can follow once the in-battle solver has been measured.

On a phone, keep the two active cards per side and add a compact **Reserves** row beneath them. Show each reserve’s name, HP, status, and whether it has fainted. Tap a reserve to edit it during setup or inspect it during replay. Keep setup and the live position separate so editing the starting roster cannot silently rewrite an in-progress battle.

When choosing a turn, show **Move** and **Switch** for each active slot. The selection UI should build a pair from the server’s legal joint actions. Selecting one switch filters the other slot’s choices, including attempts to send both slots to the same reserve. The strategy view should name both Pokémon on a switch and present the full action pair, for example, “Switch Garchomp → Charizard + Rotom-Wash uses Protect.” Slot marginals can summarize switch frequency while the joint recommendation preserves which choices are meant to be played together.

When a knockout or a pivot move requires a replacement, show a separate **Choose replacement** step. If only one player has a replacement request, the other side reads **Waiting**. A replacement can resume the same turn, so advance and undo operate on decision steps and display the actual engine turn number.

## Engine and replay

The pinned Ninjask engine already enumerates switches in `Battle::joint_choices`. In a local engine probe with four Pokémon per side, it allowed a double switch to distinct reserves, excluded using the same reserve twice, and allowed the switched-out pair to come back. The app currently caps the roster at two in `src/battle.rs` and filters voluntary switches in `src/actions.rs`. Its switch descriptions also omit the incoming Pokémon, and `src/policy.rs` gives non-move choices empty features.

1. Accept one to four brought Pokémon, validate species and item clauses across the entire roster, and encode starting lead order. Preserve the meaning of existing two-Pokémon saves, share links, CLI fixtures, and replay strings. Start with native explicit teams and replay. Expand advanced projection inputs only after a round-trip validator exists for the new states.
2. Treat roster identity, active slot, and engine team index as separate values. Ninjask swaps team entries when a Pokémon switches, so the frontend must read each slot’s current occupant from the server. Maintain a stable roster identity from initial slots across Mega Evolution, form changes, and replay. Use the engine’s canonical choice at the current step for submission and record the choice and seed for deterministic replay. Never interpret an old `switch 3` against a different board.
3. Return the decision kind, which sides need a choice, the legal joint choices, and structured move, switch, and pass details. Reuse engine legality, including trapping, recharge, Mega limits, and available reserves. Build each submitted pair from the same pre-submission state. A replacement request with a queued continuation is a separate engine state and needs explicit replay tests. For a one-sided solve, model the waiting side as having one no-op action, and submit only to the side that needs a choice.
4. Keep HP, status, PP, item consumption, Mega state, field effects, and volatile cleanup consistent across a switch. Let the engine resolve priority, target positions, entry abilities, and the rest of the queue after a pivot. A side loses when its eligible team is exhausted, including its reserves. Avoid reconstructing these transitions from UI values.

**Correctness gate.** Compare the pinned engine with its Showdown reference on small seeded traces. Cover move plus switch, double switch in either order, attacks into a switched slot, ally targets, trapping, both sides needing replacements, two empty slots with one reserve, pivot and item-triggered replacements, entry abilities including Intimidate and weather, and switch-out cleanup and persistence. Include replay, undo, save/share migration, terminal states, and the existing no-reserve fixtures. Test whether the engine resumes the same queued turn before shipping forced-replacement recommendations.

## Search that earns its recommendations

The engine probe produced 94 joint choices against 142 for one illustrative position, or 13,348 action pairs. At 32 rollouts per pair that is 427,136 simulations, and four-Pokémon battles can require longer rollouts. Other sets and positions can produce substantially different counts. Profile branching, rollout length, sampling throughput, cancellation, memory, and time to first usable result before changing web limits.

- **First release.** Keep exhaustive sampling as the reference for smaller positions. Add a switch-aware continuation policy that can value safer incoming matchups, surviving a likely KO, preserving a valuable Pokémon, and creating speed or positional advantages. Check the incoming Pokémon against plausible opponent action pairs from the same pre-choice state. Penalize aimless switch cycles in policy scoring while retaining terminal battle utility of win 1, draw 0.5, loss 0. Use seeded random as a sanity check and compare against the existing greedy and tactical baselines. A root recommendation can only be as useful as the follow-up play it assumes.
- **Larger positions.** Start with a small set of complete action pairs on both sides. Cover credible attacks, protection, single switches, and double switches where legal. Seed the set with policy scores, solve the reduced matrix, then sample responses to the other side’s current mix and add alternatives that could improve it. Revisit uncertain high-impact comparisons and periodically look outside the initial shortlist. Compare the result to dense search on small inputs before making this the default for large inputs.
- **Expose limits.** Label results by search mode. Show legal choices versus considered choices, completed and unresolved simulations, and uncertainty. Report a full-root response bound only when the search has the evidence to bound omitted alternatives on both sides. A small gap within a reduced matrix gives no such guarantee. Leave a sample missing or censored when the budget ran out, and avoid giving a precise switch recommendation when the leading lines cannot be distinguished.

## Training and validation

1. **Build a benchmark before training.** Freeze a position set spanning full four-Pokémon openings, midgame pivots, forced replacements, and small endgames. Include informative defensive positions such as a threatened lead with a favorable reserve, a credible double switch, and a tempting switch that loses momentum. Keep all positions from the same game or closely related team matchup in the same split so training cannot leak into validation.
2. **Measure the handcrafted policy first.** Run paired, side-swapped seeded matches against several opponents and record win/draw/loss, coverage, truncations, and runtime. Inspect selected switch lines against deeper or exhaustive references where feasible. Check matchups individually so a gain against one opponent cannot hide a failure against another.
3. **Train an action prior after the benchmark is stable.** Generate positions from a mix of policies and search-guided self-play. Use stronger search distributions as supervision where they are reliable, mask illegal choices, and score joint actions using active and reserve state. Use the model first to order candidates while retaining a way for search to recover overlooked actions. Promote it only if held-out paired results or time-to-quality improve at the same budget.
4. **Consider learned value later.** Train from completed terminal outcomes with separate calibration on held-out teams and opponents. Keep any learned value used for shortcuts distinct from completed rollout outcomes. Test it against small exact references and longer rollouts before relying on it for 4v4 recommendations.

## First implementation milestone

Build the roster and replay path end to end before expanding search. The acceptance case is a phone-width workflow that brings four per side, sets leads, submits a move-plus-switch, chooses a forced replacement after a knockout, undoes and replays the same sequence, and re-solves the resulting position. The existing two-Pokémon flow should pass alongside it. Full-information 4v4 is the first usable target. Hidden reserves, unknown sets, tournament team preview strategy, and full-game equilibrium are later research problems.
